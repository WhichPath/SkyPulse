# SkyPulse 离线两阶段逆地理编码技术规范 (Offline Reverse Geocoding)

## 1. 概述与设计背景

### 1.1 背景痛点
原版本 SkyPulse 依赖高德地图 Android 定位 SDK 及高德 Web API 进行逆地理编码：
1. **高延迟**：单次网络逆地理请求耗时在 1500ms ~ 3000ms 以上，严重拖慢首屏天气呈现速度；
2. **外部依赖与配额风险**：依赖商业服务 API Key，受限于配额限制及网络连通性；
3. **精度与匹配度割裂**：和风天气气象格点是基于纯经纬度插值的（物理精度达 1km 格点级），而商业地图逆地理经常在区县与道路 AOI 之间做商业化泛化，无法精确对齐民政部最新法定乡镇街道名称。

### 1.2 目标指标
* **查询延迟**：手机本地内存中两阶段匹配，平均耗时 **< 1.0 ms**；
* **网络流量**：**0 次网络请求**，100% 离线运行；
* **覆盖范围**：覆盖全国 31 个省市自治区所有 **2,900 个** 县级行政区及 **39,188 个** 民政部最新法定乡镇街道；
* **包体体积**：压缩后资源占用 **< 2.5 MB**。

## 2. 两阶段查询架构设计 (Two-Stage Architecture)

```
用户手机 GPS (经度, 纬度)
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ 阶段一：法定区县空间命中 (Point-in-Polygon)            │
│ 1. Bounding Box (外包矩形) 快速筛选候选区县 (< 0.1ms)   │
│ 2. 射线法 (Ray-Casting) 精确命中法定县级多边形 (< 0.5ms)│
│                                                        │
│ 产出：100% 准确命中的法定区县代码 (如 500157 两江新区) │
└────────────────────────────────────────────────────────┘
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ 阶段二：县域内部最近乡镇驻地检索 (Nearest Township)    │
│ 1. 仅在该区县下辖的平均 10~20 个乡镇中检索 (< 0.05ms)   │
│ 2. 计算与各乡镇驻地中心坐标的欧氏距离                  │
│ 3. 取距离最近者，返回民政部 2026 官方标准名称          │
└────────────────────────────────────────────────────────┘
       │
       ▼
格式化地名结果：[省名] [市名] [区县名] [乡镇街道名]
```

## 3. 拓扑无缝性保证 (Watertight Topology)

天地图（2024）作为国家测绘法定边界，缺乏最新设立的重特大功能性行政区（如重庆两江新区 500157、黑龙江加格达奇区 232761）。
为了杜绝直接并入新多边形产生的空隙（Gaps）与重叠（Overlaps），算法在构建期实施了**硬外壳约束差集剪裁**：
1. 提取宿主区县（如江北、渝北、北碚）的封闭联合边界（Union Shell）；
2. 新区多边形向外溢出的部分强制截断于宿主联合外壳内；
3. 宿主区县各自减去新区多边形，实现四区数学级无缝自洽。

## 4. 移动端运行期资源规范

### 4.1 数据文件
* `assets/geo/counties.bin`：2,900 个区县的外包框与简化顶点流（定点整数编码，经纬度乘以 100,000 保存为 32-bit int）；
* `assets/geo/townships.bin`：39,188 个乡镇的结构化紧凑记录，按 `county_id` 升序聚集排列，支持区县锁定后的直接二分寻址：
  ```text
  [6字节 ext_id][2字节 county_index][4字节 int_lon][4字节 int_lat][1字节 name_len][UTF-8 name_bytes]
  ```

### 4.2 内存驻留
* 数据常驻内存开销控制在 **4 MB** 以内，查询时零额外对象分配，极速响应。
